# RUNTIME GUARD RULES: Attendance V2

## Objective
Document the active Phase 01 guard rules that make V1 the only executable user-facing engine.

## Evidence from actual repo files
- `apps/frontend/src/features/attendance/runtime/attendanceRuntimeGuard.ts`: guard function and `IS_ATTENDANCE_V2_IMPLEMENTED=false`.
- `apps/frontend/src/features/attendance/runtime/attendanceRuntime.config.ts`: config can carry requested and resolved engine values.
- `apps/frontend/src/features/attendance/runtime/AttendanceRuntimeRoute.tsx`: non-V1 runtime reaching the route still renders V1 fallback.
- `apps/frontend/src/features/attendance/runtime/attendanceRuntime.test.ts`: tests default V1, invalid config fallback, V2 fallback, and disabled-mode fallback.

## Findings
The guard is a fail-closed layer. It does not trust config blindly and it does not activate V2 in Phase 01.

## Guard rules
| Input condition | Guard result |
|---|---|
| Missing config | default config resolves V1 and guard is safe. |
| Invalid engine value | unsafe, reason `invalid-config`, forced V1 active. |
| Invalid mode value | unsafe, reason `invalid-config`, forced V1 active. |
| Mode `disabled` | unsafe, reason `unsafe-mode`, forced V1 active. |
| Engine `v2` while V2 flag false | unsafe, reason `v2-not-implemented`, forced V1 active. |
| Engine `v1`, mode `active` | safe, V1 active. |

## Development warning
When V2 is requested while not implemented, a safe warning is logged only in development mode. Production users do not see a console warning generated by this path.

## Risks
- `HIGH`: changing `IS_ATTENDANCE_V2_IMPLEMENTED` without export/table gates would allow unsafe activation.
- `MEDIUM`: future remote config must keep emergency V1 priority higher than local override.

## Safe next action
Keep guard tests as the first regression check for any future runtime work.

## Blockers
- No Phase 02+ work may relax the guard unless an explicit phase acceptance criterion requires it.
